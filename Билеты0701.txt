### БИЛЕТ №1
Теоретический вопрос 1. Основные положения теории баз данных.
Теория баз данных базируется на нескольких фундаментальных концепциях, главная из которых — это модель данных (способ описания структуры и ограничений).
1.  Уровни абстракции (архитектура ANSI/SPARC):
          Внешний уровень (пользовательский): Как отдельные группы пользователей видят данные (представления).
          Концептуальный уровень (логический): Общее описание структуры всей базы без привязки к физическому хранению (таблицы, связи, ограничения).
          Внутренний уровень (физический): Как данные реально хранятся на дисках (индексы, файлы, распределение по кластерам).
2.  Независимость данных:
          *Логическая независимость:* возможность менять структуру таблиц (добавлять поля), не переписывая существующие приложения.
          *Физическая независимость:* возможность менять способ хранения (например, переносить таблицы на другой диск), не меняя логическую схему.
3.  Основные свойства (ACID):
          Atomicity (Атомарность): Транзакция выполняется либо целиком, либо не выполняется вовсе.
          Consistency (Согласованность): После транзакции база переходит из одного целостного состояния в другое (не нарушаются ограничения, ключи).
          Isolation (Изоляция): Параллельные транзакции не влияют друг на друга.
          Durability (Долговечность): Зафиксированные данные сохраняются даже при перезагрузке сервера.
4.  Модели данных:
          *Иерархическая* (дерево).
          *Сетевая* (графы).
          *Реляционная* (таблицы) — доминирует в индустрии.
          *Постреляционная/NoSQL* (документы, ключ-значение) — для специфических задач (высокая нагрузка, неструктурированные данные).

Теоретический вопрос 2. Язык манипулирования данными SQL: основные команды и возможности.
DML (Data Manipulation Language) — это подмножество SQL для работы с содержимым таблиц, а не с их структурой.
Основные команды DML:
1.  `SELECT` — выборка данных (самая сложная и гибкая). Возможности:
          Фильтрация (`WHERE`).
          Сортировка (`ORDER BY`).
          Группировка (`GROUP BY`) и агрегация (`COUNT`, `SUM`, `AVG`, `MAX`, `MIN`).
          Соединение таблиц (`JOIN`, `LEFT JOIN`, `RIGHT JOIN`).
          Подзапросы (вложенные `SELECT`).
          Оконные функции (`ROW_NUMBER()`, `RANK()`, `LAG()`, `LEAD()`).
2.  `INSERT` — добавление новых строк.
          `INSERT INTO table VALUES (...)` — добавление одной записи.
          `INSERT INTO table (col1, col2) SELECT ...` — вставка результата запроса.
3.  `UPDATE` — изменение существующих данных.
          Всегда рекомендуется использовать с `WHERE`, чтобы не обновить всю таблицу. Возможности: обновлять по условию, обновлять сразу несколько полей, использовать подзапросы для расчета новых значений.
4.  `DELETE` — удаление строк.
          Удаление по условию (`WHERE`). Без `WHERE` удалит все строки (но структура таблицы останется).
          Отличие от `TRUNCATE` (DDL): `TRUNCATE` удаляет всю таблицу физически и сбрасывает счетчик автоинкремента, работает быстрее, но не логируется постренно.

Практическое задание: Создать таблицы и установить связи между ними.
*Предположим, мы проектируем базу данных для учета студентов и их оценок. Выполним все шаги в `MySQL`.*
Шаг 1: Создание базы данных.
```sql
CREATE DATABASE IF NOT EXISTS University;
USE University;
```
Шаг 2: Создание таблицы "Группы" (родительская).
```sql
CREATE TABLE Groups (
    group_id INT PRIMARY KEY AUTO_INCREMENT, -- Уникальный идентификатор
    group_name VARCHAR(20) NOT NULL UNIQUE,  -- Название группы уникально
    year_of_admission YEAR NOT NULL
);
```
Шаг 3: Создание таблицы "Студенты" (дочерняя).
```sql
CREATE TABLE Students (
    student_id INT PRIMARY KEY AUTO_INCREMENT,
    full_name VARCHAR(100) NOT NULL,
    birth_date DATE,
    group_id INT, -- Внешний ключ
    -- Устанавливаем связь (Foreign Key)
    CONSTRAINT fk_student_group
        FOREIGN KEY (group_id) REFERENCES Groups(group_id)
        ON DELETE SET NULL  -- Если удаляем группу, у студентов ставим NULL
        ON UPDATE CASCADE   -- Если изменился ID группы, обновится автоматом
);
```
Шаг 4: Создание таблицы "Предметы".
```sql
CREATE TABLE Subjects (
    subject_id INT PRIMARY KEY AUTO_INCREMENT,
    subject_name VARCHAR(100) NOT NULL UNIQUE,
    hours INT DEFAULT 36
);
```
Шаг 5: Создание таблицы "Оценки" — *связь многие-ко-многим* между студентами и предметами.
```sql
CREATE TABLE Grades (
    grade_id INT PRIMARY KEY AUTO_INCREMENT,
    student_id INT NOT NULL,
    subject_id INT NOT NULL,
    grade_value INT CHECK (grade_value >= 2 AND grade_value <= 5), -- Ограничение
    grade_date DATE DEFAULT (CURRENT_DATE),
    -- Две связи
    CONSTRAINT fk_grade_student
        FOREIGN KEY (student_id) REFERENCES Students(student_id)
        ON DELETE CASCADE, -- Если студент удален, удаляем его оценки
    CONSTRAINT fk_grade_subject
        FOREIGN KEY (subject_id) REFERENCES Subjects(subject_id)
        ON DELETE RESTRICT -- Нельзя удалить предмет, если есть оценки
);
```
Итог: Мы создали 4 таблицы и установили 3 связи (между `Students` и `Groups`, `Grades` и `Students`, `Grades` и `Subjects`). Типы связей:
1. `Groups` → `Students`: Один-ко-многим (1:N).
2. `Students` → `Grades`: Один-ко-многим (1:N).
3. `Subjects` → `Grades`: Один-ко-многим (1:N), что в итоге дает связь Многие-ко-многим между студентами и предметами через промежуточную таблицу.

### БИЛЕТ №2
Теоретический вопрос 1. Принципы построения концептуальной модели данных.
Концептуальная модель (инфологическая) — это максимально абстрактное описание предметной области, независимое от конкретной СУБД.
Принципы построения:
1.  Выявление сущностей (Entity): Определяем объекты, информацию о которых будем хранить (например: «Клиент», «Заказ», «Товар»). Сущности должны иметь смысл для бизнес-процесса.
2.  Определение атрибутов: Характеристики сущностей. Важно выделить *идентифицирующий атрибут* (первичный ключ на логическом уровне). Атрибуты должны быть атомарными (неделимыми). Например, атрибут «Адрес» лучше разбить на «Город», «Улица», «Дом».
3.  Установление связей (Relationships):
          1:1 (Один к одному) — редкость, обычно объединяют в одну таблицу.
          1:N (Один ко многим) — например, один автор пишет много книг.
          M:N (Многие ко многим) — например, студенты и курсы. В реляционной модели такая связь разрешается через создание промежуточной (ассоциативной) сущности.
4.  Определение ограничений целостности:
          Целостность сущности: Каждый экземпляр сущности должен быть уникален (первичный ключ не может быть NULL).
          Ссылочная целостность: Внешние ключи должны указывать на существующие записи или быть NULL.
5.  Нотация представления: Обычно используется нотация «Сущность-Связь» (ER-диаграммы) в виде «вороньей лапки» (Crow's Foot) или диаграммы UML.

Теоретический вопрос 2. Запросы на выборку: сортировка и группировка данных.
Эти две операции являются основой аналитических отчетов.
1.  Сортировка (`ORDER BY`):
          Сортирует результат запроса по одному или нескольким столбцам.
          `ASC` (по возрастанию) — по умолчанию.
          `DESC` (по убыванию).
          *Важно:* сортировка выполняется в самом конце, после выборки и группировки. Можно сортировать по псевдонимам столбцов, созданным через `AS`.
          Пример: `ORDER BY salary DESC, last_name ASC;` (сначала самые большие зарплаты, если равны — по алфавиту фамилии).
2.  Группировка (`GROUP BY`):
          Используется для объединения строк с одинаковыми значениями в итоговые группы.
          Применяется только вместе с агрегатными функциями (`COUNT`, `SUM`, `AVG`, `MIN`, `MAX`), так как `SELECT` может содержать либо столбец из `GROUP BY`, либо результат агрегации.
          Правило: Любой столбец в `SELECT`, не являющийся агрегатной функцией, обязан находиться в `GROUP BY`.
          Фильтрация групп (`HAVING`): В отличие от `WHERE` (фильтрует строки до группировки), `HAVING` фильтрует уже созданные группы. Пример: `HAVING COUNT(*) > 5` (оставить только группы, где больше 5 записей).
Пример запроса с тем и другим:
```sql
SELECT 
    city, 
    COUNT(*) AS employee_count, 
    AVG(salary) AS avg_salary
FROM employees
WHERE hire_date > '2020-01-01'  -- Фильтр строк
GROUP BY city                   -- Группируем по городам
HAVING AVG(salary) > 50000      -- Фильтр групп (оставляем города с зп выше 50к)
ORDER BY avg_salary DESC;       -- Сортируем по убыванию средней зп
```

Практическое задание: Выполнить запросы на выборку с сортировкой и группировкой.
*Используем созданную ранее БД `University`.*
Задание 1 (Группировка + Сортировка): Вывести список групп, количество студентов в каждой группе и средний возраст студентов, отсортированный по убыванию количества.
```sql
SELECT 
    g.group_name,
    COUNT(s.student_id) AS total_students,
    TIMESTAMPDIFF(YEAR, AVG(s.birth_date), CURDATE()) AS avg_age
FROM Groups g
LEFT JOIN Students s ON g.group_id = s.group_id
GROUP BY g.group_id, g.group_name
ORDER BY total_students DESC;
```
Задание 2 (Сортировка по нескольким полям): Вывести всех студентов определенной группы (например, 'А-101'), отсортированных по году рождения (младшие сверху), а внутри года — по алфавиту.
```sql
SELECT full_name, birth_date
FROM Students
WHERE group_id = (SELECT group_id FROM Groups WHERE group_name = 'А-101')
ORDER BY birth_date DESC, full_name ASC;
```
Задание 3 (Группировка с вычислением): Вывести количество оценок "5" по каждому предмету.
```sql
SELECT 
    sub.subject_name,
    COUNT(*) AS count_fives
FROM Grades gr
JOIN Subjects sub ON gr.subject_id = sub.subject_id
WHERE gr.grade_value = 5
GROUP BY sub.subject_id, sub.subject_name
ORDER BY count_fives DESC;
```

### БИЛЕТ №3
Теоретический вопрос 1. Разграничение прав пользователей в СУБД.
Разграничение доступа — это механизм безопасности, определяющий, какие операции может выполнять пользователь с объектами базы.
Основные концепции в SQL (на примере MySQL, PostgreSQL):
1.  Пользователи: Учетные записи, под которыми подключаются к СУБД. Идентифицируются логином и хостом (например, `'admin'@'localhost'`).
2.  Привилегии (Privileges): Права на выполнение конкретных действий:
          Глобальные: `SUPER`, `RELOAD`, `SHUTDOWN` (управление сервером).
          Объектные: `SELECT`, `INSERT`, `UPDATE`, `DELETE`, `ALTER`, `CREATE`, `DROP`, `INDEX` на конкретных таблицах, базах данных или столбцах.
3.  Роли (Roles): Группы прав. (MySQL 8.0+). Вместо того чтобы выдавать 10 прав каждому из 50 менеджеров, мы создаем роль `manager_role`, выдаем права роли, а затем назначаем эту роль пользователям.
Команды SQL для управления доступом:
      Создание пользователя:
    `CREATE USER 'user1'@'%' IDENTIFIED BY 'strong_password';` (% — любой хост).
      Выдача прав:
    `GRANT SELECT, INSERT ON University.* TO 'user1'@'%';`
      Выдача всех прав с возможностью передачи другим:
    `GRANT ALL PRIVILEGES ON *.* TO 'admin'@'localhost' WITH GRANT OPTION;`
      Отзыв прав:
    `REVOKE INSERT ON University.* FROM 'user1'@'%';`
      Применение изменений:
    `FLUSH PRIVILEGES;`
---
Теоретический вопрос 2. Хранимые процедуры: назначение и особенности.
Хранимая процедура — это именованный блок кода на языке SQL (или процедурном расширении, типа PL/pgSQL или T-SQL), который сохраняется на сервере БД.
Назначение:
1.  Инкапсуляция бизнес-логики: Сложные операции (например, расчет зарплаты с налогами) выполняются на стороне сервера.
2.  Повторное использование: Один раз написали — вызываем тысячи раз из разных приложений.
3.  Повышение производительности: Снижается трафик "клиент-сервер" (передается только имя процедуры и параметры, вместо гигантских запросов). СУБД кеширует план выполнения процедуры.
4.  Безопасность: Можно дать пользователю право выполнять процедуру (`EXECUTE`), но не давать права на изменение таблиц напрямую.
Особенности:
      Поддерживают входные (`IN`), выходные (`OUT`) и двунаправленные (`INOUT`) параметры.
      Внутри можно использовать переменные, циклы (`LOOP`, `WHILE`), условные операторы (`IF`, `CASE`).
      Могут управлять транзакциями (`COMMIT`, `ROLLBACK`) внутри себя (зависит от СУБД).

### БИЛЕТ №4
Теоретический вопрос 1. Триггеры: что это и как они работают.
Триггер (Trigger) — это особый тип хранимой процедуры, который автоматически запускается (срабатывает) при наступлении определенного события с таблицей.
Как работает:
1.  Привязка: Триггер привязывается к конкретной таблице.
2.  Событие: Срабатывает на `INSERT`, `UPDATE` или `DELETE`.
3.  Время: Может сработать ДО (BEFORE) выполнения операции или ПОСЛЕ (AFTER) нее.
4.  Контекст строк: Внутри триггера доступны специальные псевдотаблицы:
          `OLD` — содержит старые значения строк (до изменения/удаления).
          `NEW` — содержит новые значения (после вставки/изменения).
          *Важно:* Триггеры срабатывают для КАЖДОЙ строки (FOR EACH ROW), затронутой операцией. Если `UPDATE` обновил 1000 строк, триггер запустится 1000 раз.
Типы:
      `BEFORE INSERT`: используется для валидации данных, форматирования, автозаполнения полей (например, склеить имя и фамилию в полное имя) до сохранения.
      `AFTER INSERT`: используется для логирования, отправки уведомлений, обновления агрегированных таблиц (например, увеличения счетчика заказов у клиента).
      `BEFORE DELETE`: предотвращает удаление важных записей.
      `AFTER DELETE`: используется для каскадной очистки или архивации.
---
Теоретический вопрос 2. Методы защиты базы данных.
Защита БД — это комплексный подход на нескольких уровнях.
Методы защиты:
1.  Физическая защита: Контроль доступа к серверному оборудованию, резервное копирование на удаленные носители, RAID-массивы для отказоустойчивости дисков.
2.  Сетевой уровень: Использование SSL/TLS шифрования для трафика между приложением и СУБД, чтобы данные нельзя было перехватить ("сниффить"). Настройка брандмауэра (Firewall) для разрешения подключений только с доверенных IP-адресов приложений.
3.  Аутентификация и авторизация (Управление доступом):
          Сложные пароли, хранение хэшей паролей в системе.
          Принцип минимальных привилегий (пользователю дается ровно столько прав, сколько нужно для работы, и ни битом больше).
4.  Шифрование данных:
          *Шифрование на диске (TDE):* БД хранится в зашифрованном виде. Если злоумышленник украдет файлы `.ibd` (MySQL) или `.mdf` (MSSQL), он не сможет прочитать данные без ключа.
          *Шифрование отдельных столбцов:* Шифруются персональные данные (паспорта, телефоны) с использованием функций SQL (`AES_ENCRYPT`, `AES_DECRYPT`).
5.  Аудит и мониторинг: Ведение журнала (лог-файлов) всех действий: кто, когда, какой запрос выполнял. Обнаружение аномальной активности (например, SELECT * FROM Users в 3 часа ночи).
6.  Защита от SQL-инъекций: Использование параметризованных запросов (Prepared Statements) на стороне приложения, что не позволяет злоумышленнику исполнить вредоносный код SQL, переданный через параметры (например, в поле ввода "Имя").

Практическое задание: Создать триггеры для автоматизации обработки данных.
*Создадим триггер для контроля качества данных. При добавлении оценки (Grade) ниже 3, триггер автоматически запишет предупреждение (симулируем это) или не даст добавить.* Также сделаем логгер.
Шаг 1: Создаем отдельную таблицу для логов (журнала событий).
```sql
CREATE TABLE Grades_Audit (
    audit_id INT PRIMARY KEY AUTO_INCREMENT,
    student_id INT,
    subject_id INT,
    old_grade INT,
    new_grade INT,
    action_type VARCHAR(20),
    change_date DATETIME DEFAULT CURRENT_TIMESTAMP
);
```
Шаг 2: Создаем триггер, который будет срабатывать ПОСЛЕ `INSERT` и `UPDATE` в таблице Grades (логирование изменений).
```sql
DELIMITER //
CREATE TRIGGER log_grade_changes
AFTER UPDATE ON Grades
FOR EACH ROW
BEGIN
    -- Если оценка реально изменилась
    IF OLD.grade_value != NEW.grade_value THEN
        INSERT INTO Grades_Audit (student_id, subject_id, old_grade, new_grade, action_type)
        VALUES (OLD.student_id, OLD.subject_id, OLD.grade_value, NEW.grade_value, 'UPDATE');
    END IF;
END; //
DELIMITER ;
```
Шаг 3: Создаем триггер `BEFORE INSERT`, который не даст записать оценку ниже 2 (минимальный балл) и автоматически проставит дату, если она не указана.
```sql
DELIMITER //
CREATE TRIGGER validate_grade_before_insert
BEFORE INSERT ON Grades
FOR EACH ROW
BEGIN
    -- Защита: если оценка меньше 2, превращаем ее в NULL или выбрасываем ошибку
    IF NEW.grade_value < 2 THEN
        SIGNAL SQLSTATE '45000' SET MESSAGE_TEXT = 'Оценка не может быть меньше 2!';
    END IF;
    
    -- Если дата не передана, ставим сегодняшнюю
    IF NEW.grade_date IS NULL THEN
        SET NEW.grade_date = CURDATE();
    END IF;
END; //
DELIMITER ;
```
Шаг 4: Проверка.
*Попытка добавить `INSERT INTO Grades (student_id, subject_id, grade_value) VALUES (1, 1, 1);` — будет отклонена с сообщением об ошибке.*
*При обновлении оценки с 3 на 4 — в таблицу `Grades_Audit` добавится строка лога.*

### БИЛЕТ №5
Теоретический вопрос 1. Резервное копирование и восстановление данных.
Резервное копирование (Backup) — это процесс создания копии базы данных для возможности восстановления в случае сбоя, ошибки пользователя или катастрофы.
Виды бэкапов:
1.  Физический (сырой) бэкап: Копирование файлов данных СУБД напрямую на уровне ОС.
          *Плюсы:* Очень быстрое восстановление.
          *Минусы:* Привязка к версии СУБД и ОС; сложно восстановить отдельную таблицу.
2.  Логический бэкап (дамп): Создание файла с командами `CREATE TABLE` и `INSERT` для воссоздания структуры и данных.
          *Плюсы:* Универсальность (можно перенести на другую версию СУБД), удобно для экспорта.
          *Минусы:* Восстановление может занимать часы на больших БД.
Стратегии бэкапа (по частоте и объему):
1.  Полный (Full): Копируется вся база целиком.
2.  Дифференциальный (Differential): Копируются только изменения с момента *последнего полного* бэкапа.
3.  Инкрементальный (Incremental): Копируются изменения с момента *последнего любого* бэкапа (полного или инкрементального).
          *Идеальная схема:* Полный бэкап в воскресенье, инкрементальные — каждый день, дифференциальные — раз в день для надежности.
Восстановление:
      Восстановление из инкрементального бэкапа требует последовательного применения всех цепочек (воскресенье -> понедельник -> вторник).
      Логические дампы восстанавливаются через выполнение SQL-скрипта.

Теоретический вопрос 2. Аудит базы данных и ведение аудиторского журнала.
Аудит БД — это система регистрации и анализа событий, происходящих с данными.
Цели аудита:
      Ответ на вопрос "Кто, что, когда и где сделал?".
      Обнаружение внутренних угроз (недовольный сотрудник пытается скачать таблицу клиентов).
      Соблюдение законодательства (например, 152-ФЗ о персональных данных — требует вести журнал доступа к персональным данным).
      Поиск ошибок в приложениях.
Что аудируем:
      Подключения и отключения пользователей.
      Изменения структуры таблиц (`DDL` операции).
      Чтение (SELECT) особо важных таблиц (например, `passports`, `credit_cards`).
      Изменения критичных данных (UPDATE зарплаты или статуса заказа).
      Попытки неудачного входа в систему.
Инструменты реализации:
1.  Встроенные средства СУБД: MySQL Enterprise Audit, PostgreSQL Audit Extension (pgAudit), Microsoft SQL Server Audit.
2.  Триггеры (как мы делали в Билете 4): Для детального логирования изменений конкретных таблиц.
3.  Общие логи (General Query Log): Включать его постоянно нельзя (сильная нагрузка), используют для отладки.
4.  Структура журнала: Обычно содержит `timestamp` (время), `user` (пользователь), `host` (IP-адрес), `query` (текст запроса), `object` (затронутая таблица), `status` (успех/ошибка).

### Билет № 6
Теоретический вопрос 1: Понятие сервера и клиент-серверная архитектура.
Сервер — это высокопроизводительный компьютер или специализированное программное обеспечение, которое управляет сетевыми ресурсами и предоставляет услуги другим компьютерам (клиентам) в сети. В контексте баз данных сервер — это компьютер, на котором установлена СУБД и хранятся сами данные.
Клиент-серверная архитектура — это модель взаимодействия, где задачи и нагрузка распределены между двумя основными компонентами: клиентом (запрашивающая сторона) и сервером (предоставляющая сторона).
Основные принципы работы:
1.  Разделение обязанностей: Клиент отвечает за пользовательский интерфейс, логику приложения и отправку запросов. Сервер отвечает за хранение данных, управление доступом, обработку запросов и обеспечение целостности данных.
2.  Взаимодействие через сеть: Клиент и сервер общаются друг с другом по сети с помощью определенных протоколов (например, TCP/IP).
3.  Централизованное управление: Все данные хранятся и управляются централизованно на сервере, что упрощает администрирование, резервное копирование и обеспечение безопасности .
4.  Масштабируемость: Такую архитектуру легко масштабировать, увеличивая мощность сервера или добавляя новые серверы.
Преимущества:
      Централизованный контроль и безопасность данных.
      Возможность совместного использования данных множеством пользователей.
      Высокая производительность за счет обработки запросов на мощном сервере.
Недостатки:
      Высокая стоимость оборудования и программного обеспечения.
      Требования к высокой пропускной способности сети.
      Сложность администрирования и настройки.
---
Теоретический вопрос 2: Основные характеристики серверов и механизмы доступа к базам данных.
Основные характеристики серверов:
      Производительность (CPU): Мощные многопроцессорные конфигурации для обработки большого количества параллельных запросов.
      Оперативная память (RAM): Большой объем RAM (часто от 64 ГБ до терабайт) для кэширования данных и ускорения выполнения запросов.
      Подсистема хранения (HDD/SSD): Высокоскоростные дисковые массивы (обычно RAID) с большим объемом для надежного хранения данных.
      Сетевой интерфейс: Высокоскоростные сетевые адаптеры (1 Гбит/с, 10 Гбит/с и выше) для быстрой передачи данных клиентам.
      Отказоустойчивость: Использование резервных блоков питания, вентиляторов, "горячая" замена дисков и другое аппаратное резервирование.
      Операционная система: Специализированные серверные ОС (например, Linux, Windows Server) .
Механизмы доступа к базам данных:
1.  API (Application Programming Interface): Библиотеки и драйверы, которые приложения используют для отправки запросов к СУБД. Самый распространенный пример — ODBC (Open Database Connectivity) и JDBC (Java Database Connectivity).
2.  Язык запросов SQL: Основной язык для взаимодействия с реляционными базами данных. Приложения формируют SQL-запросы и отправляют их через API.
3.  Хранимые процедуры: Код, который хранится и выполняется непосредственно на сервере БД. Клиент может просто вызвать процедуру, передав параметры, что уменьшает сетевой трафик и повышает безопасность .
4.  Веб-сервисы и REST API: Доступ к данным через HTTP-протокол, часто в формате JSON или XML. Распространен в современных веб-приложениях.

### Билет № 7
Теоретический вопрос 1: VPS, VDS и облачные серверы: определения и отличия.
      VPS (Virtual Private Server) и VDS (Virtual Dedicated Server) — это практически синонимы. Оба термина обозначают виртуальный выделенный сервер, который создается на физическом сервере с помощью технологий виртуализации (например, KVM, Xen). Каждый VPS/VDS имеет свои выделенные ресурсы (CPU, RAM, дисковое пространство), собственную ОС и может быть перезагружен независимо от других виртуальных машин. Основное отличие между терминами (VPS vs VDS) — это, как правило, лишь маркетинговое, хотя иногда VDS позиционируется как более мощное решение с гарантированными ресурсами (с использованием "жесткой" виртуализации).
      Облачные серверы (Cloud Servers) — это услуга, которая предоставляет вычислительные ресурсы по запросу через интернет. Ключевое отличие от VPS/VDS в следующем:
    1.  Масштабируемость: Облачные ресурсы можно легко и быстро масштабировать вверх или вниз (добавить RAM, CPU) в зависимости от нагрузки.
    2.  Оплата по факту использования: В отличие от фиксированной платы за VPS/VDS, в облаке вы платите только за потребленные ресурсы (Pay-As-You-Go).
    3.  Физическая инфраструктура: VPS/VDS обычно базируется на одном физическом сервере. В облачной среде виртуальные машины распределяются по кластеру физических серверов, что обеспечивает высокую отказоустойчивость.

Теоретический вопрос 2: Серверные операционные системы.
Серверная операционная система (ОС) — это платформа, предназначенная для выполнения серверных приложений и предоставления сетевых услуг. Основные особенности:
      Стабильность и непрерывная работа: Рассчитаны на длительное время работы без перезагрузок (uptime).
      Многозадачность и многопоточность: Способность эффективно обрабатывать множество параллельных запросов от тысяч пользователей.
      Безопасность: Продвинутые механизмы контроля доступа, управления пользователями и шифрования.
      Администрирование: Инструменты для удаленного управления.
Основные представители:
      Linux-дистрибутивы: Доминируют в серверной среде. Популярны Ubuntu Server, Red Hat Enterprise Linux, CentOS, Debian .
      Windows Server: Предлагает интеграцию с экосистемой Microsoft, Active Directory, .NET и популярен в корпоративных средах, использующих Windows-приложения.
      UNIX-подобные системы: Например, FreeBSD, используемый для высоконагруженных серверов.

Практическое задание: Удалённое администрирование Linux сервера.
Цель — продемонстрировать навыки управления сервером через удаленное подключение.

          Использовать команду: `ssh user_name@server_ip_address`.

Основные шаги для установки MySQL на Unix (например, Ubuntu/Debian) из официального репозитория:

          Установить уровень валидации пароля.
          Установить пароль для root-пользователя.
          Удалить анонимных пользователей.
          Отключить удаленный вход для root.
          Удалить тестовую базу данных.
          Перезагрузить таблицы привилегий.

Теоретический вопрос 2: Установка MySQL в Windows-системах: особенности.
Особенности установки:
1.  Установщик: Используется MSI-установщик MySQL Installer или ZIP-архив.
2.  Интерактивный процесс: Процесс установки проходит в графическом интерфейсе, включающем шаги по выбору типа установки (Developer Default, Server Only и т.д.).
3.  Настройка как службы Windows: MySQL автоматически настраивается и регистрируется как служба Windows (MySQL Service). Это позволяет запускать и останавливать сервер через консоль управления службами (`services.msc`) или через командную строку (`net start MySQL`).
4.  Конфигурационный файл: Файл `my.ini` (в отличие от `my.cnf` в Unix) находится в папке установки MySQL (например, `C:\ProgramData\MySQL\MySQL Server X.Y\`).
5.  Настройка безопасности: Во время установки предлагается задать пароль для root, выбрать способ аутентификации (например, использование сильного шифрования паролей), и настроить учетные записи пользователей.

    ```bash
    sudo mysql -u root -p
    ```
    Ввести пароль, установленный на шаге 5.

### Билет № 9
Теоретический вопрос 1: Организация защиты на сервере: фаерволл и брендмауэр.
Фаерволл (Firewall) / Брендмауэр — это система сетевой безопасности, которая отслеживает и контролирует входящий и исходящий сетевой трафик на основе заранее установленных правил безопасности. По сути, это барьер между доверенной внутренней сетью и недоверенными внешними сетями (например, Интернет).
Организация защиты:
1.  Правила фильтрации: Фаерволл имеет набор правил, которые определяют, какой трафик разрешен, а какой запрещен. Правила строятся на основе:
          IP-адресов (источник/назначение).
          Портов (например, открыт порт 80 для HTTP, 443 для HTTPS, 3306 для MySQL).
          Протоколов (TCP, UDP, ICMP).
2.  Пример на Linux (UFW): `sudo ufw allow from 192.168.1.100 to any port 22` — разрешить SSH-доступ только с определенного IP-адреса.
3.  Состояние (Stateful) и без состояния (Stateless): Современные файрволлы (stateful) отслеживают состояние соединений, автоматически разрешая ответный трафик от внутренних серверов.
4.  Дополнительные функции: Многие современные файрволлы включают возможности обнаружения вторжений (IDS/IPS) и контроля приложений.

Теоретический вопрос 2: Виртуализация: понятие и основные виды.
Виртуализация — это технология, которая позволяет создавать виртуальную версию аппаратного обеспечения, операционной системы, сетевых ресурсов или хранилища. Основная цель — эффективное использование физических ресурсов сервера, изоляция приложений и упрощение управления .
Основные виды виртуализации:
1.  Виртуализация серверов (аппаратная виртуализация). На одном физическом сервере запускаются несколько виртуальных машин (ВМ), каждая со своей ОС. Гипервизор (например, VMware ESXi, Microsoft Hyper-V, KVM) управляет этими ВМ, выделяя им ресурсы .
2.  Виртуализация на уровне ОС (контейнеризация). В отличие от ВМ, контейнеры (например, Docker) используют ядро хост-ОС и изолируют приложения на уровне пользовательского пространства. Это более легковесный и быстрый способ.
3.  Виртуализация сети (NFV). Сетевые функции, такие как файрволлы, маршрутизаторы, балансировщики нагрузки, реализуются в виде программных приложений на стандартных серверах.
4.  Виртуализация хранилищ. Физическое дисковое пространство из разных устройств объединяется в единый пул для управления.

Цель: Обеспечить минимальный уровень защиты сервера от внешних угроз.
План работы:
1.  Обновление системы: Установить последние обновления безопасности.
    ```bash
    sudo apt update && sudo apt upgrade -y
    ```
2.  Настройка фаерволла:
          Разрешить только необходимые порты (SSH, HTTP, HTTPS).

      ```bash
      sudo ufw allow ssh
      sudo ufw allow http
      sudo ufw allow https
      sudo ufw enable
      ```

          Редактировать файл `/etc/ssh/sshd_config`.
          Найти и изменить строку: `PermitRootLogin no`.

          Предоставить права sudo: `sudo usermod -aG sudo admin_user`.
5.  Вход на сервер только через ключи SSH (опционально, но рекомендуется):
          Сгенерировать SSH-ключ на клиенте (`ssh-keygen`).
          Скопировать публичный ключ на сервер (`ssh-copy-id admin_user@server_ip`).
          Отключить аутентификацию по паролю в `/etc/ssh/sshd_config` (`PasswordAuthentication no`).

### Билет № 10
Теоретический вопрос 1: Гипервизоры: виды и функции.
Гипервизор (Hypervisor) или монитор виртуальных машин (VMM) — это программное обеспечение, которое создает и запускает виртуальные машины, управляя их доступом к физическому аппаратному обеспечению.
Основные функции:
      Изоляция ресурсов: Обеспечивает независимость ВМ друг от друга.
      Управление ресурсами: Распределяет CPU, RAM, хранилище и сетевые ресурсы между ВМ.
      Создание и управление ВМ: Запуск, остановка, приостановка и миграция ВМ.
Виды гипервизоров:
1.  Гипервизор Type 1 (Bare-Metal). Работает непосредственно на физическом оборудовании, без хост-ОС. Обеспечивает высокую производительность и безопасность. Используется в центрах обработки данных.
          Примеры: VMware ESXi, Microsoft Hyper-V, KVM (Linux), Xen.
2.  Гипервизор Type 2 (Hosted). Работает как приложение внутри существующей операционной системы.
          Примеры: Oracle VirtualBox, VMware Workstation, Parallels Desktop. Используется для тестирования и разработки.

### Билет №11
Теоретические вопросы:
1. Контейнеризация: что это и зачем нужна.
      Что это: Контейнеризация — это метод виртуализации на уровне операционной системы, который позволяет запускать изолированные друг от друга пользовательские пространства (контейнеры) на одном ядре хостовой ОС. В отличие от виртуальных машин (ВМ), контейнер не содержит в себе полноценную гостевую ОС. Вместо этого он включает в себя само приложение, все его зависимости (библиотеки, конфигурационные файлы, переменные окружения) и минимальный набор системных утилит, необходимых для его работы.
      Зачем нужна:
          Изоляция: Обеспечивает независимость приложений друг от друга. Сбой в одном контейнере не влияет на работу других.
          Легковесность и скорость: Контейнеры запускаются за секунды, так как им не нужно загружать ОС. Они потребляют меньше ресурсов, чем ВМ.
          Переносимость (Portability): Контейнер с приложением и всеми его зависимостями гарантированно будет работать одинаково на любой системе, где установлен Docker (или другой движок контейнеризации): на локальной машине разработчика, в тестовой среде или в облаке. Это решает проблему «у меня работает, а на сервере — нет».
          Управление версиями и CI/CD: Образы контейнеров можно версионировать, хранить в реестрах и использовать в пайплайнах непрерывной интеграции и доставки (CI/CD) для автоматизации развертывания.
          Микросервисная архитектура: Контейнеризация является идеальной основой для микросервисов, позволяя развертывать, масштабировать и обновлять каждый сервис по отдельности.
2. Docker и Docker контейнеры: основные понятия.
      Docker: Это открытая платформа для разработки, доставки и запуска приложений в контейнерах. Это, по сути, самый популярный движок контейнеризации, который предоставляет удобный интерфейс и инструменты для управления контейнерами.
      Основные понятия Docker:
          Docker Daemon (демон): Фоновый процесс, который работает на хостовой машине и управляет всеми объектами Docker (контейнерами, образами, сетями, томами). Он слушает запросы от Docker CLI.
          Docker CLI (клиент): Командная строка `docker`, с помощью которой пользователь взаимодействует с демоном (например, `docker run`, `docker build`, `docker pull`).
          Docker Image (образ): Это неизменяемый (read-only) шаблон, который содержит все необходимое для запуска приложения: код, среду выполнения, системные инструменты, библиотеки и настройки. Образ является основой для контейнера. Его можно сравнить со слепком или классом в ООП.
          Docker Container (контейнер): Это запущенный экземпляр образа Docker. Это исполняемый пакет, который содержит все для запуска приложения и изолирован от других процессов. Контейнер — это «живой» объект, который можно запускать, останавливать, перемещать или удалять. Сравним с экземпляром класса в ООП.
          Dockerfile: Это текстовый файл, содержащий инструкции (команды) для сборки образа. В нем описывается, на основе какого базового образа строить, какие файлы скопировать, какие команды выполнить и т.д.
          Docker Registry (реестр): Это хранилище для Docker-образов. Самый популярный публичный реестр — Docker Hub. Вы можете использовать его для поиска и скачивания готовых образов (например, `mysql`, `ubuntu`, `nginx`) и для загрузки своих собственных.

Практическое задание: Использование Docker контейнеров.
*Цель: Установить Docker, скачать образ и запустить контейнер с базой данных MySQL, а затем подключиться к ней.*
Пошаговый план:
1.  Установка Docker:
          Для Linux (Ubuntu/Debian):
        ```bash
        sudo apt update
        sudo apt install docker.io
        sudo systemctl start docker
        sudo systemctl enable docker
        # Добавить пользователя в группу docker, чтобы не использовать sudo
        sudo usermod -aG docker $USER
        # Выйти и зайти заново или выполнить newgrp docker
        ```
          Для Windows/macOS: Скачать и установить Docker Desktop с официального сайта.
          Проверка: `docker --version`
2.  Скачивание (pull) образа MySQL:
          Откройте терминал и выполните команду для скачивания последней версии образа MySQL из Docker Hub:
        ```bash
        docker pull mysql:latest
        ```
          *Объяснение:* Эта команда находит образ `mysql` с тегом `latest` в реестре и загружает его на ваш компьютер.
3.  Запуск контейнера:
          Запустите контейнер с именем `my-db`, задав пароль для root-пользователя и пробросив порты:
        ```bash
        docker run --name my-db -e MYSQL_ROOT_PASSWORD=my-secret-pw -p 3306:3306 -d mysql:latest
        ```
          *Разбор команды:*
              `docker run` — команда для создания и запуска контейнера.
              `--name my-db` — задаем имя контейнеру.
              `-e MYSQL_ROOT_PASSWORD=my-secret-pw` — передаем переменную окружения с паролем root (требуется для MySQL).
              `-p 3306:3306` — пробрасываем порт. `3306` на вашей хост-машине будет маппиться на `3306` порт внутри контейнера. Теперь к БД можно обращаться с `localhost:3306`.
              `-d` — запускает контейнер в фоновом режиме (detached mode).
4.  Проверка статуса:
          Убедитесь, что контейнер запущен:
        ```bash
        docker ps
        ```
          В выводе вы увидите ваш контейнер `my-db` со статусом `Up`.
5.  Подключение к СУБД внутри контейнера:
          Выполните команду, чтобы запустить оболочку `bash` внутри запущенного контейнера:
        ```bash
        docker exec -it my-db bash
        ```
          Теперь вы внутри контейнера. Подключитесь к MySQL из командной строки:
        ```bash
        mysql -u root -p
        ```
        Введите пароль `my-secret-pw`, когда будет запрошено.
          Вы успешно попали в MySQL. Можете выполнить запрос для проверки: `SHOW DATABASES;`
          Выйдите из MySQL (`exit`) и из контейнера (`exit`).
6.  Остановка и удаление контейнера (для очистки после работы):
          Остановить контейнер: `docker stop my-db`
          Удалить контейнер: `docker rm my-db`

### Билет №12
Теоретические вопросы:
1. Оркестраторы контейнеров: Docker Swarm.
      Что такое оркестрация: Управление группой контейнеров на множестве хостов. Это включает в себя развертывание, масштабирование, обеспечение отказоустойчивости, обновление, управление сетями и безопасностью.
      Docker Swarm: Это нативный инструмент оркестрации, встроенный непосредственно в Docker. Он превращает группу Docker-хостов в единый виртуальный кластер.
      Основные особенности:
          Простота настройки: Интегрирован в Docker CLI. Инициализируется одной командой (`docker swarm init`), добавление узлов — другой (`docker swarm join`).
          Декларативный подход: Вы описываете желаемое состояние сервиса в файле (композиции), и Swarm поддерживает его.
          Масштабируемость: Легко масштабировать сервисы, указывая количество реплик (`docker service scale my-service=5`).
          Самоисцеление (Self-healing): Если узел или контейнер падает, Swarm автоматически запускает новый экземпляр для поддержания заявленного количества реплик.
          Роллинг-апдейты (Rolling updates): Позволяет обновлять приложения без простоя, постепенно заменяя старые контейнеры новыми.
          `Swarm` проще в освоении, чем Kubernetes, но уступает ему в гибкости и в возможностях для сложных сценариев.
2. Нереляционные базы данных: основные типы и особенности.
      Особенности (NoSQL):
          Не используют традиционную реляционную модель (таблицы, строки, столбцы с жесткой схемой) и язык SQL (хотя могут иметь свои языки запросов).
          Схема не обязательна (Schema-less): Данные в одной коллекции/таблице могут иметь разную структуру, что упрощает внесение изменений.
          Масштабируемость: Легко масштабируются горизонтально (распределяются на множество серверов). Это их главное преимущество для Big Data и высоконагруженных систем.
          Отказ от ACID в пользу BASE: Обычно жертвуют строгой согласованностью (Consistency) в пользу доступности (Availability) и устойчивости к разделению (Partition tolerance) — по теореме CAP.
      Основные типы:
    1.  Ключ-Значение (Key-Value): Самая простая структура. Как гигантский словарь или Map. Примеры: Redis, Memcached. Используются для кеширования, хранения сессий.
    2.  Документо-ориентированные (Document-oriented): Хранят данные в виде документов (обычно в JSON или BSON). Каждый документ содержит пары полей и значений. Это очень гибко и интуитивно для разработчиков. Примеры: MongoDB, CouchDB.
    3.  Колоночные (Column-family): Хранят данные не в строках, а в столбцах, сгруппированных в семейства столбцов. Это обеспечивает высокую производительность для аналитических запросов и агрегаций по большому количеству данных. Примеры: Cassandra, HBase.
    4.  Графовые (Graph): Специализированы для работы со связанными данными (узлы и ребра). Очень эффективны для социальных сетей, поиска путей, рекомендательных систем. Примеры: Neo4j, JanusGraph.

          *Выбор/Создание базы данных:* В MongoDB база данных и коллекция создаются автоматически при первой вставке документа. Переключимся на базу `mydb`: `use mydb`
          CREATE (Вставка):
              Вставьте один документ в коллекцию `users`:
            ```javascript
            db.users.insertOne({ name: "Alice", age: 30, city: "New York" })
            ```
              Вставьте несколько документов:
            ```javascript
            db.users.insertMany([{ name: "Bob", age: 25, city: "London" }, { name: "Charlie", age: 35, city: "Moscow" }])
            ```
          READ (Чтение):
              Найти все документы в коллекции: `db.users.find()`
              Найти с условием (фильтром): `db.users.find({ city: "Moscow" })`
              Найти одного пользователя по имени: `db.users.findOne({ name: "Alice" })`
              Красивый вывод: `db.users.find().pretty()`
          UPDATE (Обновление):
              Обновить возраст пользователя с именем Alice:
            ```javascript
            db.users.updateOne({ name: "Alice" }, { $set: { age: 31 } })
            ```
            *Важно:* `$set` — оператор, который обновляет только указанные поля.
              Проверить изменение: `db.users.find({ name: "Alice" })`
          DELETE (Удаление):
              Удалить пользователя с именем Bob:
            ```javascript
            db.users.deleteOne({ name: "Bob" })
            ```
              Проверить: `db.users.find()`
4.  Выход и очистка:
          Выйти из `mongosh`: `exit`
          Выйти из контейнера: `exit`
          (Опционально) Остановить и удалить контейнер: `docker stop some-mongo && docker rm some-mongo`

### Билет №13
Теоретические вопросы:
1. Документно-ориентированные СУБД: особенности.
      Центральная идея: Данные хранятся не в нормализованных таблицах с жесткими связями, а в виде автономных документов. Эти документы являются самодостаточными и содержат в себе все данные об объекте, часто со вложенными структурами.
      Особенности:
          Гибкая схема (Schema-less): Это ключевое отличие. Документы в одной коллекции не обязаны иметь одинаковый набор полей. Это позволяет легко адаптировать модель данных под изменяющиеся требования бизнеса без миграций схемы.
          Формат хранения: Чаще всего используется JSON или его бинарная версия BSON (как в MongoDB). Это нативно поддерживается языками программирования, что устраняет несоответствие между объектами в коде и таблицами в БД (объектно-реляционное несоответствие).
          Производительность: Быстрый доступ к документу целиком. Если вы часто читаете всю информацию о пользователе вместе с его заказами, хранить это в одном документе эффективнее, чем делать JOIN нескольких таблиц в реляционной БД.
          Масштабируемость: Легко масштабируются горизонтально с помощью шардинга (распределения данных по разным серверам), так как документы не имеют жестких связей между собой.
          Слабая поддержка транзакций (ACID): Традиционно жертвовали транзакционностью в пользу производительности и масштабируемости. Однако современные решения (например, MongoDB) уже вводят поддержку транзакций, аналогичную реляционным БД, но в более ограниченном виде.
2. Очереди сообщений и Redis.
      Очереди сообщений: Это механизм асинхронного обмена данными между компонентами системы (микросервисами). Производитель (Producer) отправляет сообщение в очередь, а потребитель (Consumer) забирает его оттуда. Это позволяет развязать компоненты и сделать систему более надежной и масштабируемой. Если потребитель временно недоступен, сообщения останутся в очереди и будут обработаны позже.
      Redis: Это высокопроизводительная СУБД типа «ключ-значение» с открытым исходным кодом, которая работает в основном в памяти (in-memory). Это делает ее невероятно быстрой.
      Что делает Redis в контексте очередей:
          Redis не является полноценным брокером сообщений (как RabbitMQ или Kafka), но он предоставляет удобные структуры данных для реализации простых очередей.
          Для создания очереди в Redis часто используют структуры данных Списки (Lists) и команды LPUSH/RPUSH (для добавления) и LPOP/RPOP (для извлечения). Это классическая FIFO (First-In, First-Out) очередь.
          Более продвинутый механизм — Redis Streams. Это лог-структурированный тип данных, который позволяет создавать надежные очереди с поддержкой групп потребителей (consumer groups), что делает Redis полноценным конкурентом для простых сценариев работы с потоками событий.
          Применение: Redis часто используется для кеширования, хранения сессий пользователей, как брокер сообщений между микросервисами в небольших проектах и как брокер для задач (task queue).

Практическое задание: Работа с Redis.
*Цель: Запустить контейнер с Redis и выполнить базовые операции по работе со списком как с очередью.*
Пошаговый план:
1.  Запуск контейнера Redis:
          Запустите контейнер с Redis в фоновом режиме:
        ```bash
        docker run --name some-redis -p 6379:6379 -d redis:alpine
        ```
          *Объяснение:* Используем легковесный образ `redis:alpine`. Порт `6379` пробрасываем на хост.
2.  Подключение к Redis:
          Выполните команду для запуска клиента `redis-cli` внутри контейнера:
        ```bash
        docker exec -it some-redis redis-cli
        ```
          Подсказка сменится на `127.0.0.1:6379>`, что означает, что вы подключены.
3.  Базовые операции с ключами и строками:
          *Установка строки:* `SET username "JohnDoe"`
          *Получение строки:* `GET username`
          *Проверка существования:* `EXISTS username` (вернет 1) и `EXISTS surname` (вернет 0).
          *Удаление ключа:* `DEL username`
4.  Реализация очереди сообщений с помощью списков (Lists):
          *Добавление элементов (Публикация):* Добавим три сообщения в очередь с помощью команды `LPUSH` (слева) или `RPUSH` (справа). Пусть левая сторона — это голова очереди (начало), правая — хвост (конец).
    ```bash
    # Добавляем сообщение в начало очереди (голова)
    LPUSH task_queue "task 1"
    # Добавляем в конец очереди (хвост)
    RPUSH task_queue "task 2"
    RPUSH task_queue "task 3"
    ```
          *Просмотр очереди:* Посмотрим все элементы очереди (слева направо):
        ```bash
        LRANGE task_queue 0 -1
        ```
        Вывод должен быть: `task 1`, `task 2`, `task 3`.
          *Извлечение элементов (Потребление):* Извлечем и удалим элемент из очереди. Будем придерживаться принципа FIFO (первый пришел — первый ушел). Для этого нужно брать элемент с конца очереди с помощью команды `RPOP` (если добавляли в начало, `LPUSH`). Если вы использовали `LPUSH` для добавления, то `RPOP` и будет правильным. Если вы всегда использовали `RPUSH`, то забирать надо `LPOP`.
    ```bash
    # Блокирующее извлечение (если очередь пуста, ждать 5 секунд)
    BRPOP task_queue 5
    ```
    *Повторите команду несколько раз, чтобы вытащить все задачи.* Вы увидите, как по очереди извлекаются `"task 1"`, `"task 2"`, `"task 3"`.
5.  Выход:
          Выйти из `redis-cli`: `exit`
          (Опционально) Остановить и удалить контейнер: `docker stop some-redis && docker rm some-redis`

### Билет №14
Теоретические вопросы:
1. Проектирование схемы данных: этапы и методы.
      Проектирование — это ключевой этап создания базы данных, определяющий ее эффективность и удобство использования.
      Основные этапы:
    1.  Анализ требований: Сбор и анализ информации о предметной области. Определение бизнес-правил, пользователей, типов данных, которые будут храниться, и операций, которые будут выполняться.
    2.  Концептуальное проектирование: Создается высокоуровневая модель данных, независящая от конкретной СУБД. Обычно используется ER-модель (Сущность-Связь). На этом этапе определяются сущности (объекты), их атрибуты (свойства) и связи между сущностями (один-к-одному, один-ко-многим, многие-ко-многим).
    3.  Логическое проектирование: Концептуальная модель преобразуется в модель данных конкретной СУБД (например, реляционную). Создаются отношения (таблицы), определяются первичные и внешние ключи. Проводится нормализация для устранения избыточности и аномалий. На выходе получается схема базы данных.
    4.  Физическое проектирование: Этот этап зависит от конкретной СУБД и оборудования. Выбираются типы данных для атрибутов, создаются индексы для ускорения запросов, настраиваются параметры хранения (размеры файлов, табличные пространства), решаются вопросы распределения данных (шардирование, репликация) и резервного копирования.
      Методы проектирования:
          Снизу-вверх (Bottom-Up): Сначала интегрируются существующие разрозненные данные (файлы, отчеты, документы) и на их основе строится общая модель. Используется редко для новых систем.
          Сверху-вниз (Top-Down): Начинается с концептуального моделирования предметной области. Бизнес-аналитики и архитекторы создают общую картину сущностей и связей, которая затем детализируется.
2. Нормализация схемы данных: цели и уровни.
      Нормализация — это процесс организации данных в реляционной базе данных для уменьшения избыточности и улучшения целостности данных.
      Главные цели:
    1.  Устранение избыточности: Исключить дублирование одних и тех же данных в разных таблицах. Это экономит место и облегчает обновление.
    2.  Устранение аномалий вставки, обновления и удаления: Сделать так, чтобы добавление, изменение или удаление одного факта требовало изменения только в одном месте.
    3.  Обеспечение зависимости по первичному ключу: Структурировать данные так, чтобы каждый атрибут однозначно зависел от полного первичного ключа.
      Основные уровни (нормальные формы):
    1.  1-я Нормальная Форма (1НФ):
              В каждой ячейке таблицы должно быть одно атомарное (неделимое) значение.
              Нет повторяющихся групп столбцов.
              *Пример:* Атрибут `Телефоны` не может содержать несколько номеров в одной строке. Их нужно вынести в отдельную таблицу.
    2.  2-я Нормальная Форма (2НФ):
              Удовлетворяет 1НФ.
              Все неключевые атрибуты полностью зависят от всего составного первичного ключа, а не от его части. Актуально для таблиц с составным ключом.
              *Пример:* В таблице `ЗаказТовары` с ключом `(ID_Заказа, ID_Товара)`, атрибут `Цена_Товара` зависит только от `ID_Товара`, а не от всего ключа. Это не соответствует 2НФ. Цену нужно вынести в таблицу `Товары`.
    3.  3-я Нормальная Форма (3НФ):
              Удовлетворяет 2НФ.
              Все неключевые атрибуты зависят только от первичного ключа и не зависят от других неключевых атрибутов (т.е., нет транзитивных зависимостей).
              *Пример:* В таблице `Сотрудники` есть поля `Город`, `Индекс`. `Индекс` зависит от `Города`, а не от `ID_Сотрудника`. Это транзитивная зависимость. Нужно вынести `Города` и `Индексы` в отдельную таблицу `Города`.

Практическое задание: Проектирование схемы данных.
*Цель: Разработать схему базы данных для небольшой системы. На примере «Интернет-магазин».*
Пошаговый план:
1.  Шаг 1: Анализ требований (Предметная область).
          В магазине есть клиенты. У каждого клиента есть Имя, Email, Адрес доставки.
          Есть товары. У товара есть Название, Описание, Цена, Количество на складе.
          Клиент может сделать заказ. Один заказ принадлежит одному клиенту. У заказа есть дата, статус, общая сумма.
          Один заказ может содержать несколько разных товаров. Один товар может быть в нескольких заказах (связь многие-ко-многим).
2.  Шаг 2: Концептуальное проектирование (ER-диаграмма).
          Выделяем сущности:
              `Клиент` (Клиент)
              `Товар` (Товар)
              `Заказ` (Заказ)
          Связи:
              `Клиент` --- `1:N` --- `Заказ` (один клиент может сделать много заказов, заказ принадлежит одному клиенту).
              `Заказ` --- `M:N` --- `Товар` (многие товары в одном заказе, один товар во многих заказах). Для этой связи нужна вспомогательная сущность `Состав заказа`.
3.  Шаг 3: Логическое проектирование (Создание таблиц).
          На основе ER-диаграммы создаем список таблиц и их атрибутов. Определяем первичные ключи (PK) и внешние ключи (FK).
    Таблица `Клиенты`:
          `Клиент_ID` (PK, Integer, автоинкремент)
          `Имя` (VARCHAR(255), NOT NULL)
          `Email` (VARCHAR(255), UNIQUE, NOT NULL)
          `Адрес` (VARCHAR(255))
    Таблица `Товары`:
          `Товар_ID` (PK, Integer, автоинкремент)
          `Название` (VARCHAR(255), NOT NULL)
          `Описание` (TEXT)
          `Цена` (DECIMAL(10, 2), NOT NULL)
          `Кол-во_на_складе` (INTEGER, DEFAULT 0)
    Таблица `Заказы`:
          `Заказ_ID` (PK, Integer, автоинкремент)
          `Клиент_ID` (FK, Integer, NOT NULL) — связывает заказ с клиентом.
          `Дата_заказа` (DATETIME, DEFAULT CURRENT_TIMESTAMP)
          `Статус` (VARCHAR(50), DEFAULT 'Новый')
          `Общая_сумма` (DECIMAL(10, 2))
    Таблица `Состав_заказа` (для разрешения связи M:N):
          `Заказ_ID` (PK, FK, Integer)
          `Товар_ID` (PK, FK, Integer)
          `Количество` (Integer, NOT NULL)
          `Цена_продажи` (DECIMAL(10, 2), NOT NULL) — цена на момент заказа.
4.  Шаг 4: Создание схемы (SQL DDL).
          Для создания этих таблиц в любой реляционной СУБД (например, PostgreSQL или MySQL) нужно написать скрипт `CREATE TABLE`. Вот пример для PostgreSQL:
    ```sql
    CREATE TABLE Клиенты (
        Клиент_ID SERIAL PRIMARY KEY,
        Имя VARCHAR(255) NOT NULL,
        Email VARCHAR(255) UNIQUE NOT NULL,
        Адрес VARCHAR(255)
    );
    CREATE TABLE Товары (
        Товар_ID SERIAL PRIMARY KEY,
        Название VARCHAR(255) NOT NULL,
        Описание TEXT,
        Цена DECIMAL(10, 2) NOT NULL,
        Кол_во_на_складе INTEGER DEFAULT 0
    );
    CREATE TABLE Заказы (
        Заказ_ID SERIAL PRIMARY KEY,
        Клиент_ID INTEGER NOT NULL REFERENCES Клиенты(Клиент_ID),
        Дата_заказа TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
        Статус VARCHAR(50) DEFAULT 'Новый',
        Общая_сумма DECIMAL(10, 2)
    );
    CREATE TABLE Состав_заказа (
        Заказ_ID INTEGER REFERENCES Заказы(Заказ_ID),
        Товар_ID INTEGER REFERENCES Товары(Товар_ID),
        Количество INTEGER NOT NULL,
        Цена_продажи DECIMAL(10, 2) NOT NULL,
        PRIMARY KEY (Заказ_ID, Товар_ID)
    );
    ```

### Билет №15
Теоретические вопросы:
1. Нормализация схемы данных: примеры и правила.
      Пример нарушения 1НФ:
          Таблица `Сотрудники_Проекты` со столбцами: `Сотрудник_ID`, `Имя`, `Проекты` (здесь перечислены проекты через запятую: "ПроектА, ПроектБ").
          *Нарушение:* Значение в ячейке `Проекты` неатомарное (неделимое), так как содержит несколько значений.
          *Решение (1НФ):* Разбить на две таблицы: `Сотрудники` и `Проекты_Сотрудников`. В таблице `Проекты_Сотрудников` каждая строка будет иметь пару `(Сотрудник_ID, Проект)`.
      Пример нарушения 2НФ:
          Таблица `Детали_Заказов` с составным ключом `(Номер_Заказа, Код_Детали)` и атрибутами: `Название_Детали` и `Количество`. `Название_Детали` зависит только от `Код_Детали`, а не от всего ключа.
          *Нарушение:* Частичная зависимость неключевого атрибута от части составного ключа.
          *Решение (2НФ):* Вынести `Код_Детали` и `Название_Детали` в отдельную таблицу `Детали`. В исходной таблице оставить `(Номер_Заказа, Код_Детали)` и `Количество`.
      Пример нарушения 3НФ:
          Таблица `Сотрудники` с атрибутами: `ID_Сотр`, `Имя`, `ID_Департамента`, `Название_Департамента`. `Название_Департамента` зависит от `ID_Департамента`, который, в свою очередь, является неключевым атрибутом (не PK).
          *Нарушение:* Транзитивная зависимость: `ID_Сотр` -> `ID_Департамента` -> `Название_Департамента`.
          *Решение (3НФ):* Создать отдельную таблицу `Департаменты` с ключом `ID_Департамента` и атрибутом `Название_Департамента`. В таблице `Сотрудники` оставить только `ID_Департамента` (как внешний ключ).
2. Создание таблиц и установление связей.
      Создание таблиц осуществляется с помощью SQL-команды CREATE TABLE.
          Указывается имя таблицы.
          Определяются столбцы (колонки) с их именами и типами данных (`INTEGER`, `VARCHAR`, `DATE`, `DECIMAL` и т.д.).
          Указываются ограничения (constraints): `PRIMARY KEY`, `FOREIGN KEY`, `NOT NULL`, `UNIQUE`, `DEFAULT`.
      Установление связей реализуется через Внешние ключи (Foreign Keys).
          Связь один-ко-многим (1:N) реализуется путем добавления столбца внешнего ключа в таблицу «многие», который ссылается на первичный ключ таблицы «один».
              *Пример:* `Заказы` (многие) имеют столбец `Клиент_ID`, который является FK и ссылается на `Клиент_ID` в таблице `Клиенты` (один).
          Связь многие-ко-многим (M:N) реализуется с помощью промежуточной (связующей) таблицы.
              *Пример:* Связь `Заказы` и `Товары` реализована через таблицу `Состав_заказа`. В этой таблице два внешних ключа: `Заказ_ID` (ссылка на `Заказы`) и `Товар_ID` (ссылка на `Товары`). Их комбинация образует составной первичный ключ этой таблицы.
          Связь один-к-одному (1:1) реализуется добавлением внешнего ключа с ограничением `UNIQUE` в одну из таблиц, чтобы гарантировать уникальность соответствия.

### Билет №16
Теоретический вопрос 1: Язык SQL: DDL и DML команды.
SQL (Structured Query Language) — это декларативный язык программирования, используемый для управления данными в реляционных базах данных. Его команды делятся на группы по функциональности:
1.  DDL (Data Definition Language) — Язык определения данных.
    Используется для создания и изменения структуры базы данных (схем, таблиц, индексов). Эти команды автоматически фиксируют транзакцию (нельзя откатить).
          `CREATE` — создает объект БД (таблицу, представление, процедуру).
          `ALTER` — изменяет структуру существующего объекта (добавляет/удаляет столбец, меняет тип).
          `DROP` — удаляет объект БД целиком (вместе со всеми данными).
          `TRUNCATE` — удаляет все строки из таблицы, освобождая память, но сохраняя структуру (быстрее, чем `DELETE` без условий).
2.  DML (Data Manipulation Language) — Язык манипулирования данными.
    Используется для извлечения, добавления, изменения и удаления непосредственно данных в таблицах. Эти команды можно откатить (используя `ROLLBACK`).
          `SELECT` — выборка данных (основная команда).
          `INSERT` — добавление новых строк.
          `UPDATE` — изменение существующих данных.
          `DELETE` — удаление строк.
Теоретический вопрос 2: Работа с данными: вставка, обновление, удаление.
Это практическая реализация DML:
      Вставка (`INSERT`):
          Добавление полной строки: `INSERT INTO Таблица VALUES (значение1, значение2, ...);` (важен порядок столбцов).
          Добавление выборочных столбцов: `INSERT INTO Таблица (столбец1, столбец3) VALUES (значение1, значение3);`.
          Копирование данных из другой таблицы: `INSERT INTO Новая_таблица SELECT * FROM Старая_таблица WHERE условие;`.
      Обновление (`UPDATE`):
          Изменяет значения в существующих строках. Крайне важен блок `WHERE`.
          Синтаксис: `UPDATE Таблица SET столбец1 = новое_значение, столбец2 = новое_значение2 WHERE условие;`.
          Если опустить `WHERE`, обновятся все строки таблицы.
      Удаление (`DELETE`):
          Удаляет строки. Также критичен `WHERE`.
          Синтаксис: `DELETE FROM Таблица WHERE условие;`.
          Без `WHERE` — удалит все записи (но в отличие от `TRUNCATE`, это можно откатить и операция работает медленнее, так как логируется каждая строка).

### Билет №17
Теоретический вопрос 1: Разграничение прав пользователей: роли и привилегии.
В СУБД (например, MySQL/PostgreSQL) безопасность строится на системе привилегий:
      Привилегия (Privilege) — это конкретное разрешение на выполнение определенного действия над объектом. Например: `SELECT` (чтение), `INSERT` (вставка), `UPDATE` (изменение), `DELETE` (удаление), `CREATE` (создание таблиц), `DROP`, `ALL PRIVILEGES` (все права).
      Роль (Role) — это поименованная группа привилегий. Роль создается один раз, а затем назначается пользователям. Это упрощает администрирование.
          *Пример:* Создается роль `Менеджер` с правами `SELECT, INSERT, UPDATE` на таблицу "Проекты".
          Когда новый менеджер приходит в компанию, мы просто выдаем ему роль `Менеджер`, а не назначаем 10 отдельных привилегий.
Теоретический вопрос 2: Создание и использование хранимых процедур.
Хранимая процедура — это набор SQL-инструкций, который компилируется один раз и сохраняется на сервере БД. Она выполняется как единый блок.
      Зачем нужны: Повторное использование кода, уменьшение трафика (мы передаем только имя процедуры и параметры, а не гигантский запрос), централизованная бизнес-логика, безопасность (можно дать права на выполнение процедуры, но не давать права на прямую работу с таблицами).
      Создание: Используется `CREATE PROCEDURE`.
      Использование (вызов): Используется `CALL`.

    ```sql
    CREATE PROCEDURE AddEmployee (
    ```

### Билет №18
Теоретический вопрос 1: Триггеры: типы и применение.
Триггер — это специальный тип хранимой процедуры, которая выполняется автоматически (в ответ на событие) при изменении данных в таблице.
      Типы по времени срабатывания:
          `BEFORE` (До) — выполняется до вставки/обновления/удаления. Используется для валидации данных или вычисления значений по умолчанию.
          `AFTER` (После) — выполняется после того, как изменения уже применены. Используется для аудита (логирования действий) или обновления агрегирующих таблиц.
      Типы по событию: `INSERT`, `UPDATE`, `DELETE`.
      Применение: Автоматическое заполнение столбцов (например, дата обновления записи `updated_at`), поддержка целостности данных (каскадные изменения), сложная бизнес-логика, аудит (запись в лог кто, когда и что изменил).
Теоретический вопрос 2: Методы защиты базы данных: шифрование и контроль доступа.
      Шифрование:
          *Шифрование на диске (Transparent Data Encryption - TDE)* — шифрует физические файлы базы данных (.ibd, .mdf), защищая от кражи файлов БД злоумышленником.
          *Шифрование столбцов (Cell-level Encryption)* — шифрует конкретные столбцы (пароли, номера карт) прямо в таблице. Расшифровка происходит только у клиента с правильным ключом.
          *Шифрование канала (SSL/TLS)* — шифрует трафик между приложением и сервером БД, защищая от перехвата данных (Man-in-the-Middle).
      Контроль доступа:
          Аутентификация — проверка логина и пароля.
          Авторизация — проверка прав (привилегий и ролей, описанных в билете 17). Также сюда входит управление подключениями (ограничение IP-адресов, с которых можно подключаться).

### Билет №19
Теоретический вопрос 1: Резервное копирование: виды и стратегии.
      Виды:
          *Физическое (сырое)* — копирование файлов данных и журналов транзакций напрямую (на уровне ОС). Быстрое, но менее гибкое.
          *Логическое* — создание дампа (скрипта SQL) с командами `CREATE` и `INSERT`. Медленнее, но позволяет восстанавливать отдельные таблицы.
      Стратегии (Full/Incremental/Differential):
          Полное (Full): Копируется вся база данных целиком. Занимает много места и времени, но дает полную точку восстановления.
          Дифференциальное (Differential): Копируются все изменения, произошедшие с момента *последнего полного* бэкапа. Для восстановления нужно: Полный бэкап + Последний дифференциальный.
          Инкрементное (Incremental): Копируются изменения, произошедшие с момента *последнего любого бэкапа* (полного или инкрементного). Экономит место, но для восстановления нужно: Полный бэкап + все инкрементные цепочкой.
Теоретический вопрос 2: Восстановление данных: процедуры и инструменты.
Восстановление должно быть протестировано заранее!
      Процедура:
    1.  Остановить сервисы, использующие БД (если возможно).
    2.  Восстановить из полной копии.
    3.  Применить дифференциальные или инкрементные бэкапы строго по порядку (по времени).
    4.  Проверить целостность данных (выполнить тестовые запросы).
    5.  Запустить приложения.
      Инструменты:
          `mysqldump` — для логического бэкапа MySQL.
          `pg_dump` / `pg_restore` — для PostgreSQL.
          `mysqlbinlog` — для восстановления на основе бинарных логов (инкрементальное).

### Билет №20
Теоретический вопрос 1: Клиент-серверная архитектура: принципы работы.
Это модель, в которой задачи распределены между поставщиком услуг (Сервер) и заказчиком услуг (Клиент).
      Клиент: Инициирует запрос (например, SQL-запрос). Отвечает за пользовательский интерфейс.
      Сервер: Всегда находится в режиме ожидания. Получает запрос, обрабатывает его, выполняет вычисления/поиск в данных и возвращает только результат (а не всю базу) клиенту.
      Принцип работы (на примере БД): Клиентское приложение подключается через сеть к порту сервера БД (например, 3306 для MySQL). После аутентификации клиент отправляет текстовый запрос. Сервер парсит запрос, оптимизирует его, выполняет чтение/запись на диск и отправляет обратно клиенту набор строк (результат).
Теоретический вопрос 2: Механизмы доступа к базам данных.
Это способы, которыми приложения подключаются к БД:
1.  JDBC (Java Database Connectivity): Стандарт для Java. Использует драйверы для подключения к разным СУБД.
2.  ODBC (Open Database Connectivity): Старый, но универсальный стандарт от Microsoft, работает на Windows.
3.  ADO.NET / Entity Framework: Стандарты для C# и .NET.
4.  Нативные драйверы: Специфичные библиотеки для конкретного языка (например, `psycopg2` для Python и PostgreSQL, `mysql-connector` для Python и MySQL).
5.  REST API / GraphQL: Современный подход, когда доступ к БД предоставляется через HTTP-запросы к промежуточному слою (бекенду), а не напрямую клиенту.

Практическое задание: Анализ серверных дистрибутивов.
*Условие: Выбор ОС для сервера БД. Сравним два популярных дистрибутива.*
Пошаговый анализ:
1.  Ubuntu Server LTS:
          *Особенность:* Самый популярный, огромное сообщество, упрощенный менеджер пакетов (`apt`).
          *Плюсы:* Легкость установки, обширная документация, быстрые обновления, идеально для начинающих.
          *Минусы:* Менее стабилен по сравнению с Red Hat на больших нагрузках, стандартное ядро не такое отполированное для критических систем.
2.  Red Hat Enterprise Linux (RHEL) или его клон AlmaLinux/Rocky Linux:
          *Особенность:* Корпоративный стандарт, менеджер пакетов `dnf/yum`.
          *Плюсы:* Высокая стабильность, длительный цикл поддержки (10 лет), сертифицирован для многих коммерческих СУБД (Oracle DB, IBM DB2).
          *Минусы:* Сложнее в настройке для новичков, для RHEL нужна платная подписка (используем бесплатные клоны).
Вывод: Для учебного проекта выбираем Ubuntu Server из-за простоты. Для крупного банка/корпорации — AlmaLinux/Rocky из-за стабильности и поддержки.

### Билет №21
Теоретический вопрос 1: Серверные ОС: обзор и особенности.
Это специализированные операционные системы, предназначенные для непрерывной работы в дата-центрах.
      Особенности:
          *Стабильность:* Работают месяцами/годами без перезагрузки.
          *Безопасность:* Строгая политика доступа, встроенные фаерволы, SELinux или AppArmor.
          *Производительность:* Оптимизация планировщика задач и файловой системы для работы с большим количеством одновременных подключений.
          *Отсутствие GUI:* Управление в основном через командную строку (SSH), чтобы не тратить ресурсы процессора на графику.
      Обзор: Linux (Ubuntu, CentOS, RHEL, Debian) — доминируют на серверах БД (около 70% рынка). Windows Server — используется для MS SQL Server и в корпоративных средах, где все на .NET.
Теоретический вопрос 2: Удалённое администрирование Linux сервера.
Это управление сервером, находясь в другой сети, через протокол SSH (Secure Shell).
      Основные инструменты:
          `ssh` (команда в терминале) или PuTTY (клиент для Windows).
          `scp` / `rsync` — для безопасной передачи файлов.
          `ssh-keygen` — генерация ключей для входа без пароля и более безопасно.
      Безопасность: Отключаем вход под `root`, используем ключи, меняем стандартный порт (22) на другой (например, 2222), чтобы снизить количество автоматических ботов.

Практическое задание: Удалённое администрирование Linux.
*Условие: У нас есть сервер с IP `192.168.1.100`.*
Пошаговый план действий:
1.  Подключение к серверу по SSH (через PuTTY или терминал):
    ```bash
    ssh user_name@192.168.1.100 -p 22
    ```
    Вводим пароль пользователя.
2.  Обновление системы и установка сервера БД (через удаленный терминал):
    ```bash
    sudo apt update           # Обновляем список пакетов
    sudo apt install mysql-server -y
    ```
3.  Настройка Firewall (UFW) удаленно:
    ```bash
    sudo ufw allow 22/tcp    # Оставляем доступ к SSH
    sudo ufw allow 3306/tcp  # Открываем порт для MySQL (если нужно)
    sudo ufw enable          # Включаем фаервол
    ```
4.  Перезапуск службы и проверка статуса:
    ```bash
    sudo systemctl restart mysql
    sudo systemctl status mysql
    ```
5.  Выход из сессии: Вводим `exit`.

### Билет №22
Теоретический вопрос 1: Установка MySQL в Unix-системах: этапы.
В большинстве дистрибутивов установка производится через менеджер пакетов (репозиторий), а не вручную из исходников.
1.  Обновление репозиториев: `sudo apt update` (Debian/Ubuntu) или `sudo dnf check-update` (RHEL/Fedora).
2.  Установка пакета сервера: `sudo apt install mysql-server` или `sudo dnf install mysql-server`.
3.  Запуск службы: `sudo systemctl start mysqld` (в CentOS/RedHat часто сразу стартует, надо проверить).
4.  Безопасная установка (скрипт): Запускается скрипт `sudo mysql_secure_installation`. Он требует: а) Установить пароль для root, б) Удалить анонимных пользователей, в) Запретить удаленный вход для root, г) Удалить тестовые базы данных, д) Применить изменения.
5.  Включение автозапуска: `sudo systemctl enable mysql`.
Теоретический вопрос 2: Установка MySQL в Windows-системах: отличия.
В Windows процесс основан на графическом установщике (MSI-инсталляторе) от Oracle.
1.  Загрузка: Скачиваем инсталлятор с официального сайта.
2.  Мастер установки (GUI): Выбираем тип (Developer Default, Server only).
3.  Настройка: Указываем порт (по умолчанию 3306), выбираем способ аутентификации (Legacy или Strong Password).
4.  Служба Windows: Сервер устанавливается как Служба Windows (Windows Service). Она автоматически запускается при старте системы.
5.  Настройка Path: Путь к папке `bin` (например, `C:\Program Files\MySQL\MySQL Server 8.0\bin`) добавляется в переменную окружения `PATH`, чтобы можно было вызывать `mysql` из командной строки из любой папки.
---
Практическое задание: Установка MySQL в Windows.
*Пошаговая инструкция (симуляция действий).*
1.  Скачиваем установщик: Идем на сайт mysql.com, скачиваем `mysql-installer-web-community-8.0.x.msi`.
2.  Запускаем инсталлятор:
          Соглашаемся с лицензией.
          Выбираем тип установки: "Server only" (для лабораторной работы подойдет).
3.  Установка: Нажимаем "Execute" — инсталлятор скачивает и ставит файлы.
4.  Настройка сервера (Configuration):
          Тип конфигурации: Development Machine (для начала).
          Сетевая настройка: оставляем порт 3306, включаем протокол TCP/IP.
          Метод аутентификации: выбираем "Use Strong Password Encryption" (новый стандарт).
          Задаем пароль для пользователя `root` (например, `MyRootPass123!`). Запоминаем его!
          Настройки службы Windows: оставляем как есть (Запуск автоматически).
5.  Применение: Нажимаем "Execute" — инсталлятор применяет настройки и создает файлы данных.
6.  Проверка: Нажимаем кнопку "Check" или открываем командную строку:
    ```cmd
    mysql -u root -p
    ```
    Вводим пароль `MyRootPass123!`. Если появилась строка `mysql>`, значит установка прошла успешно.
